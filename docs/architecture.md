# Match119 전체 시스템 아키텍처 (Cloud Storage 기반 메인 흐름)

> 원본: 팀 기획 문서 「Match119 전체 시스템 아키텍처.docx」를 옮긴 것. 흐름도는 [sequence-diagram.jpg](sequence-diagram.jpg) 참고.
>
> **현재 구현 기준 참고 (원문과 다른 점)**
> - 구현 범위는 클라우드 파이프라인(Step 1~5)까지. 온디바이스 모드(아래 Firestore ③)는 현재 범위 밖이다.
> - "이어올리기(resumable)"는 아직 미구현(예정). 현재 계획은 단순 PUT Signed URL.
> - Lifecycle 정책의 최소 단위는 1일이다. "즉시 파기"는 Cloud Run의 삭제 호출에만 해당한다.
> - "처리 소요 시간 18초", "지연 시간 0에 가깝게", "4분을 18초로" 등은 **기획 단계의 예시·목표치이며 실측값이 아니다.** 실측 전에는 코드·문서·발표에서 완료형으로 쓰지 않는다.
> - 우리의 GCS 원본 삭제와 Google 측 Zero Data Retention(ZDR) 설정은 별개 개념이다.

## Step 1: 현장 고지 및 데이터 라우팅 (프론트엔드 - Flutter)

동의 시 (메인 파이프라인 시작): 최고 성능을 내기 위해 데이터가 클라우드로 향하는 통로를 엽니다. UI 멈춤 방지를 위해 비동기(Asynchronous) 스레드에서 오디오 캡처를 시작합니다.

## Step 2: 고속/안정적 데이터 업로드 (스토리지 - Cloud Storage)

**Signed URL 발급:** 데이터가 무거워질 때 앱이 직접 서버로 텍스트(Base64)를 쏘면 용량이 30% 커지고 네트워크 병목이 생깁니다. 대신 Flutter 앱은 백엔드(Cloud Run)에 "파일을 안전하게 올릴 일회용 주소(Signed URL)"를 요청합니다.

**다이렉트 바이너리 업로드:** 오디오(.wav)와 이미지(.jpg) 원본 파일을 변환 없이 가장 가벼운 상태로 Cloud Storage에 업로드합니다. 구급차의 통신이 불안정해도 '이어올리기'가 지원되어 가장 빠르고 안전하게 전송됩니다. *(이어올리기: 미구현, 예정)*

## Step 3: 서버리스 백엔드 오케스트레이션 (미들웨어 - Cloud Run & Firestore)

**데이터 조립:** 업로드가 완료되면 서버리스 백엔드인 Cloud Run이 작동합니다. 파일 자체를 다운로드하지 않고, 스토리지에 저장된 파일의 주소(`gs://bucket-name/audio.wav`)만 가져옵니다.

**프롬프트 주입:** Cloud Run은 Firestore DB에서 '119 구급시스템 단일 텍스트창 서식'에 맞춘 최신 프롬프트를 불러온 뒤, 앞서 확보한 파일 주소(gs://)들과 결합하여 매우 가벼운 JSON 페이로드로 묶어냅니다.

## Step 4: 네이티브 멀티모달 추론 (AI 엔진 - Vertex AI)

**내부망 고속 통신:** Cloud Run이 주소(URI)를 넘겨주면, Vertex AI 인프라가 작동합니다. 이때 구글 클라우드의 내부 백본망(Backbone)을 사용해 Storage의 대용량 데이터를 직접 읽어 들입니다. *(원문 "지연 시간 0에 가깝게"는 미검증 표현)*

**직접 추론:** STT 변환을 거치지 않습니다. Gemini 모델이 환자의 거친 숨소리와 상처 이미지를 직접 듣고 보면서, 구급일지의 통합 텍스트창에 들어갈 수 있는 '단일 요약 템플릿'을 만들어 냅니다.

## Step 5: 흔적 지우기 및 OS 클립보드 매핑 (보안/UX)

**백엔드 클린업 (중요):** Vertex AI가 분석 결과를 반환하는 즉시, Cloud Run은 Cloud Storage에 임시로 올라갔던 환자의 오디오와 사진 파일을 영구 삭제(Delete)합니다. 혹시 모를 오류에 대비해 스토리지 '수명 주기(Lifecycle)' 정책도 이중으로 걸려 있습니다(1일 경과 후 자동 삭제). 이후 Firestore에는 민감 정보를 제외한 처리 소요 시간 같은 메타데이터만 로깅합니다.

**Zero-typing 매핑:** 최종 정제된 텍스트는 Flutter 앱으로 돌아옵니다. 대원이 화면의 '복사' 버튼을 누르면 OS의 클립보드(Clipboard)에 데이터가 매핑되고, 대원은 기존 국가망 119 구급시스템 앱을 열어 '붙여넣기' 함으로써 기록을 완료합니다. 최종 확인·전송의 주체는 항상 대원이다.

## 구성 요소별 역할

### 1. Cloud Storage — "안전한 임시 보관함 (File Storage)"

오디오(.wav), 사진(.jpg) 같은 '무거운 파일(바이너리 데이터)'을 안전하게 옮기고 임시로 담아두는 창고 역할을 합니다.

- **역할 요약:** 불안정한 모바일 네트워크 환경에서 큰 파일을 업로드받는 역할.
- **왜 필요한가:** 데이터베이스(Firestore)나 코드 실행기(Cloud Run)는 큰 파일을 저장하고 주고받는 데 적합하지 않습니다. 무거운 데이터를 Cloud Storage에 먼저 올려두면, 백엔드 서버는 파일을 직접 들고 다닐 필요 없이 가벼운 주소(URI)만 주고받으며 AI와 통신할 수 있어 시스템 전체가 가벼워집니다.
- **보안 역할:** 영구 저장소가 아닙니다. AI의 분석이 끝나면 즉시 파일이 파기되는 '휘발성 보안 금고' 역할을 수행합니다.

### 2. Cloud Run — "백엔드 총괄 매니저 (Compute / Middleware)"

데이터를 저장하지 않는 서버리스(Serverless) 컴퓨팅 서비스로, 전체 프로세스를 지휘하는 오케스트레이터 역할을 합니다.

- **역할 요약:** 앱, Storage, Firestore, Vertex AI 사이에서 타이밍에 맞게 명령을 내리고 데이터를 조립하는 '두뇌'이자 '교환원'.
- **하는 일:**
  1. 앱에서 "스토리지에 파일 올렸어!"라는 신호를 받음.
  2. Firestore에서 최신 119 요약 프롬프트를 가져옴.
  3. 프롬프트와 스토리지 주소(URI)를 묶어서 Vertex AI로 보냄.
  4. AI의 결과를 받으면, Storage에 방금 쓴 파일 삭제(Delete)를 명령함.
  5. 앱(Flutter)으로 최종 텍스트 결과를 돌려줌.
- **왜 필요한가:** 앱이 직접 Vertex AI나 Storage 삭제 명령을 제어하면 앱이 무거워지고 보안 키 유출 위험이 큽니다. Cloud Run을 중간에 두어 클라이언트(앱)와 AI를 안전하게 격리합니다.

### 3. Firestore — "규칙서 및 시스템 기록부 (NoSQL DB)"

파일 저장은 Cloud Storage, AI 연산은 Vertex AI, 중간 통제는 Cloud Run이 하는데도 데이터베이스가 필요한 이유는 다음과 같습니다.

**① 프롬프트의 '동적 관리 (Dynamic Prompting)' (가장 중요)**

프롬프트를 Flutter 앱 코드 안에 하드코딩하면, 국가 119 시스템의 서식이 바뀌거나 프롬프트를 개선할 때마다 앱을 수정해 스토어 '업데이트 심사'를 올려야 합니다(수일 소요). 프롬프트를 Firestore에 텍스트로 저장해 두면, 관리자가 프롬프트를 수정하는 즉시 현장 앱에 새 지시사항이 적용됩니다. 앱 업데이트 없이 시스템을 개선할 수 있습니다. *(서버에 캐시를 두면 "즉시"가 아니라 "캐시 TTL 이내 반영")*

**② 개인정보가 배제된 '감사 로그 (Audit Log)' 수집**

환자의 민감한 의료 정보(음성, 사진, 요약 내용)는 즉시 파기되지만, 시스템 통계는 남겨야 합니다. Firestore에는 "출동 건 시각 / 처리 소요 시간 / 통신 상태: 성공 / 파일 용량" 같은 비식별 메타데이터만 로깅합니다. 이 데이터는 시간 단축 효과를 보여 주는 핵심 성과 지표(KPI)의 실측 근거가 됩니다.

**③ 오프라인(온디바이스) 모드 상태 동기화** — *현재 구현 범위 밖*

환자가 동의를 거부해 네트워크가 차단된 '온디바이스 모드'로 작동할 때, 기기 내부에 사용 로그를 저장해 두었다가 와이파이 연결 시 클라우드로 동기화하는 구상. (이 방식은 앱이 Firestore에 직접 접근해야 하므로 "앱은 Cloud Run만 호출" 원칙과 충돌 — 구현 시 재설계 필요)
